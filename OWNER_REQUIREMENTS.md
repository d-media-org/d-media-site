# d . media — Owner Requirements

## Purpose

Този документ съдържа постоянните изисквания на Project Owner.

При конфликт между основните AIOS документи се следва този ред:

1. `AGENTS.md`
2. `OWNER_REQUIREMENTS.md`
3. `CHECKLIST.md`
4. `SOP-001-EXECUTE_TASK.md`
5. `PROJECT.md`
6. `KNOWLEDGE_BASE.md`

## Brand

- Официалното име винаги се изписва `d . media`.
- Не използвай `d.media`, `d-media`, `D Media` или `D.media`, освен при техническо ограничение.
- Не променяй публичното позициониране на `d . media` без изрично указание.

## Public Identity

- Project Owner е вътрешна роля.
- Не публикувай самоличността на Project Owner.
- Не използвай лично име за Project Owner в документацията.
- Не създавай Founder, Owner или About the Founder страници.
- Не добавяй JSON-LD Person, schema с име на Project Owner, meta данни, footer credits, copyright или други публични елементи, които идентифицират Project Owner.

## Design

- Проектът се развива еволюционно.
- Не допускай редизайн без изрично указание.
- Не променяй логото, логотипа, цветовата система, типографията, spacing системата, дизайн езика или анимациите без разрешение.

## Code

- Предпочитай минимален diff.
- Не добавяй зависимости без реална необходимост.
- Не прави рефактори извън задачата.
- Не редактирай несвързани файлове.
- Преди създаване на нов компонент провери дали вече няма подходящ.
- Не допускай дублиране на компоненти или логика.

## Architecture

- Project Owner взема окончателните решения за production deploy, brand identity, pricing, legal документи и архитектурни промени.
- Предпочитай поправка на причината, а не на симптома.
- Не използвай временни решения, ако проблемът може да бъде решен архитектурно.
- Използвай съществуващите механизми и абстракции.
- Не създавай паралелна логика за вече решен проблем.

## Assets

- Всички изображения използват съществуващия asset pipeline.
- Не създавай втори asset pipeline.
- Не използвай hardcoded asset paths.
- Не заобикаляй съществуващия asset resolver.
- Не използвай source asset, когато проектът вече има optimized asset pipeline.

## Video

- Всички видеа трябва да имат thumbnail/poster.
- Native `<video>` трябва да използва `poster`.
- Embedded video/card употреба трябва да има thumbnail image.
- Poster изображенията използват съществуващия asset resolver.
- Не използвай временни или hardcoded video poster решения.
- Не използвай poster изображения, които не са достъпни публично.
- Не допускай 404 за video poster изображения.
- Не допускай layout shift, причинен от липсващ poster.

## SEO/GEO/AI

- Не допускай промяна, която влошава Lighthouse, SEO, GEO или AI visibility.
- Не премахвай schema без изрична задача.
- Не премахвай `llms.txt` без изрична задача.
- Не премахвай sitemap без изрична задача.
- Не премахвай robots правила без изрична задача.

## QA

- Не приключвай задача без изпълнение на изискваните проверки.
- Не твърди, че нещо е поправено, ако не е проверено.
- Не пропускай browser QA, когато промяната засяга визуално поведение.
- Когато промяната е визуална, провери responsive поведение, console errors и network errors.

## Documentation

- `OWNER_REQUIREMENTS.md` е единственият източник на истина за постоянните изисквания на Project Owner.
- При откриване на ново постоянно изискване го добави в този документ.
- Не създавай нови документи, ако съществуващите могат да бъдат разширени.
- Не дублирай информация между документи без ясна причина.
- Не оставяй един и същ факт на повече от едно място без ясна причина.

## Quality Standards

- Всеки нов код трябва да бъде съобразен със съществуващата архитектура.
- Предпочитай разширяване на съществуваща функционалност пред създаване на нова.
- Ако има централен resolver, helper или utility, използвай него.
- След всяка промяна изпълни всички приложими проверки.
- Минималният набор за website/code промени е lint, build, Astro build и Cloudflare validation.

Definition of Done:

- функционалността работи;
- няма регресии;
- няма build грешки;
- няма lint грешки;
- няма нови 404;
- няма нови console errors;
- няма нови network errors;
- няма необходими допълнителни ръчни проверки, освен ако те не са извън възможностите на локалната среда.

## Never Again

- Не започвай безкрайни цикли от анализи, предложения и планове.
- След одобрение от потребителя започни работа незабавно.
- Не повтаряй вече обяснени неща.
- Не предлагай нова архитектура, ако не е поискана.
- Не редактирай файлове извън обхвата на задачата.
- Не прави “полезни” рефактори, ако не са поискани.
- Не създавай втори механизъм, когато вече съществува централен.
- Не използвай hardcoded пътища към изображения, видеа или други ресурси.
- Не добавяй `<video>` без poster.
- Не публикувай самоличността на Project Owner.
- Не добавяй JSON-LD, meta или footer информация, която идентифицира Project Owner.
- Не допускай промяна, която влошава PageSpeed без основателна причина.
- Не увеличавай ненужно JavaScript bundle-а.
- Не зареждай ресурси, които не са необходими.
- Всяка новооткрита повтаряща се грешка трябва да бъде добавена в този раздел, за да не се допуска повторно.
